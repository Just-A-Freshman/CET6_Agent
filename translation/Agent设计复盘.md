# 1. 架构
整个Agent有三个核心能力。下面逐个讲解。

## 1.1 六级翻译出题

六级翻译出题，有两种模式。真题模式 VS 考点模式。真题模式是最开始时默认的模式，如果用户对真题回答的评分低于某个阈值后，视为没有充分掌握考点，会自动进入考点模式。用户也可以选择强行回到真题模式。这一部分使用工作流实现，依赖一个六级翻译句子切分的**真题数据库**。

1. 真题模式：基于已有的2016-2015年近10年的57套六级翻译真题中拆分出来的333个句子，随机抽取1个句子作为考题。这可以认为是基准考题；
2. 考点模式：基于前一道出的真题，由LLM模仿编制的，有相似考点的题目。用于强化对考点的练习。



## 1.2 规范化的评价输出

这一部分我将一个标准的评价拆分为五个核心部分：

第一个部分是纠错，用两个LLM接力完成。第二个部分是纳入错题考点数据库，这一部分由”基于定义“的LLM版决策树和数据库插入的代码构成；第三部分是评分，让一个LLM在充分参考前两个LLM的输出结果的情况下，结合考题和用户答案，给出三个部分的评分。第四个部分是错误重现，核心依靠前面第二部分的规范化实现，直接使用代码读取“错题考点数据库”输出；第五个部分是参考译文的给出，由一个LLM在仅参考第一个LLM的修改建议的情况下，给出最小化的参考译文。整个部分是通过一个复杂的工作流实现了。

下面分别阐述各个组成部分的细节：

1. 第一个部分，LLM#1在**不深度思考**的情况下，尽可能多地对照题目和翻译原文，纠出用户的错误，输出包括“编号”、“错误描述”、“错误片段”和“修改建议”的json文件，其核心是发散地找出用户尽可能多地潜在错误，避免遗漏。LLM#2则需要开启深度思考，它负责依据LLM#1的纠错标准，对照着检查LLM#1的错误归错部分，它只有删除权力而没有修改权力。为了保证这一点，它只被允许输出被错误归错的编号列表，从根本上防止了它修改原错误总结列表。随后接入一个代码部分，删除对应被错误归错的内容；
2. 第二个部分，可以认为是整个设计的核心与难点，就是给第一部分LLM给出的给出的错误列表中的每一个错误，贴上清晰而准确的类别标签，以便后续第四部分的错误重现，强化用户对考点的掌握。我们事先通过多个LLM的反复迭代，得到包含了彼此间不重合，语义清晰的38类错误类型表。但是实战时发现，如果将整个错误类型表丢给LLM去分类，结果惨不忍睹：由于38类错误的定义复杂，内容庞大，直接丢给LLM会导致上下文溢出，进而产生极为严重的幻觉。解决思路便是预先构造一颗“决策树”，把38类错误以树状结构层层划分。当LLM需要判定一段描述到底属于什么类型的错误时，不再需要一次性读取38条定义描述——它只被要求做一个更高层级的归类，比如只负责判断，这个错误到底是信息完整度，语言准确性还是流畅度的错误，接着再将错误导入下一个层级。依次类推，每一个层级都有一个LLM坚守，负责将一个错误描述归入下一个层级，而每个层级都只有8个及以下的节点。通过这种预先的“注意力引导”机制，极大地降低了LLM在给错误贴类别标签时的准确性。最后，第一部分的错误描述输出和第二部分的错误类别输出合为一体，注入到“**错题考点数据库**”中。实现上，这一部分是用到了**Coze的云端IDE插件**，不过美中不足的是我必须用到外部API，也就意味着决策树类别判断的LLM实际上不依赖于Coze内部的LLM，而需要外部的API Key。这使得用户使用时理应当自行输入自己的API KEY，带来了一定的不便。而目前我还暂时没有暴露这个输入，也就是还是在用自己的API KEY硬编码到工作流之中。
3. 第三部分比较简单，它只负责结合前面的错误表进行评分。为什么不把评分任务丢给LLM#1呢？前面提到，LLM#1负责发散性归错，如果让它进行评分，可能导致评分偏低；LLM#2负责错误收敛，如果让它评分，整个任务就会非常混杂。让一个单独的LLM评分，能充分结合前面两个LLM的成果，给出尽可能客观的评分。
4. 第四部分完全由代码实现，它深刻依托第二部分的“错题考点数据库”。只需要在第二部分得到对应的错误类型后，到数据库中查询对应名称的用户错误并展示即可。
5. 第五部分是参考译文的给出，同样由一位LLM负责。理论上来说它似乎可以归入第三部分的LLM来实现，不过为了职责的清晰，我还是将它单独划分了出来emmmmmmm；



## 1.3 知识总结

知识总结实际上完全由代码实现。没错，它其实深刻依赖于第二个核心功能。实际上，在第二个核心功能中，每当用户完成一次题目作答，翻译题目 + 用户回答 + 参考答案 都会插入到“**用户回答表**”中。再结合之前的“**错题考点数据库**”，两张标在设计之初就通过`question_id`进行连接。不过有一个细节：Coze中的数据库不允许多表查询，所以实际上这里的多表查询是通过for循环节点实现的，效率肯定不如直接多表查询来的高效，但也的的确确是将两张表联系在了一起。最后，将查询到的结果通过代码渲染节点，结构化的返回出去。





# 2. 细节补充

实际开发过程中还是遇到了不少的问题。

1. 如何给出规范化的六级翻译评分？在最开始开发时，我实际上并没有去查询六级翻译的评分标准，而是简单地采用逐点扣分的形式，结果因为很多小错误导致扣分离谱。我甚至视图给不用的错误加权，但结果依然不尽人意，而且扣分往往没有上限；因此，我在后改进过程中自主查询了六级翻译标准，核心是三个层面：信息完整性，语言准确性，流畅度，各5分，并且批改看的是整体效果而不是逐点扣分。这其实也是将“评分和纠错”分开的一个关键原因。纠错的LLM总是不由自主地在纠错过程中给翻译逐点扣分，而忽视了整体效果。单独拎出一个LLM评分，既看整体效果，也看过去的纠错成果，充分将评分客观化；
2. 如何让LLM输出结构化的Json数据？这实际上并不是一件简单的事。我的做法实际上非常朴素，用一个代码做兜底。在LLM提示词部分，用一个清晰的例子说明Json的结构；在LLM输出后，先接一个我写的云端插件（普通的代码节点没办法调用第三方库，文档中写明了只允许numpy和asyio requests_async，但云端插件可以自由安装第三方库，提供了最大限度的灵活性），调用了`repair_json`这个开源的Github第三方库。这样一来，我就保证了json数据至少是语法规范的。那结构呢？实际上经过我的反复尝试，结构几乎不会出现问题。如果出现了问题，基本是由于用户提示词部分就已经出现了问题。这里在工程上严格来说应该要对Json的结构再做一层校验，不过我这边考虑到出错概率实在太低，而且并不应用于生成环境，因此没有再附加冗余代码做结构校验。
3. 工作流的特殊机制：在实际工作中，我发现Agent调用工作流，会导致**记忆的刷新**。什么意思呢？设想一下，如果你让Agent回答一个问题，Agent在回答到一半的时候，突然调用一个工作流，结果一瞬间，Agent好像对刚才回答了一半的内容完全没有了记忆，又开始根据工作流的内容进行输出。这似乎是因为工作流的设计机制。与之相对的，调用插件时，Agent会在拿到插件的输出结果后继续做思考；而如果是RAG知识库，则是用户在输入问题时直接将用户的问题去查询知识库，然后一并将搜索结果塞给LLM。这三种模式可以看出，工作流应当是用于完全处理一个问题的，换言之，LLM在遇到对应问题时，只需要调用工作流就可以解决这个问题，而不需要附带做其他思考；插件则适合渐进式地使用，让LLM在思考过程中做自主决策；RAG知识库则适合在用户问出私有化的问题时使用，显然对于我们这种场景是不适用的。综合来看，我在设计时就刻意让工作流都能完成一个完整的任务，而不是一个任务的局部。比如出题工作流，它不能仅仅是告诉LLM要出什么题，而是要完成输出一道题目；评价工作流，需要完整输出对用户评价的所有内容等等。
4. 整个Agent设计到的组件：
    - 4个数据库：“用户回答表”、“错题考点数据库”、“真题数据库”和“错误类型表（决策树结构）”
    - 4个工作流：出题工作流（简单）、评价工作流（核心，非常复杂）、内容总结工作流（简单）、获取配置工作流（简单）
    - 2个插件：LLM决策树归类插件（复杂）、Json数据处理插件（简单，只是调用`repair_json`）
5. 用户变量：
    - `is_good`：布尔值，表示用户翻译得好不好，默认为1
    - `current_question`：当前出的题目
    - `current_exam_point`：当前总结的考点
    - `target_score`：用户想要达到的目标分数，默认为10
    - `API_KEY`：用户使用模型的API KEY
    - `BASE_URL`：模型的base_url，默认为`https://api.deepseek.com/v1`
    - `MODEL`：模型名称，默认为`deepseek-v4-flash`
